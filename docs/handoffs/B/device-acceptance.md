# 실제 iPhone 검증 기록

2026-09-25 실제 **iPhone 16 Pro Max / iOS 27.2 / Safari 27.2**를 USB로 연결해 B 렌더러를 검증했다. Xcode에서 wired·paired·booted인 실제 기기를 확인하고, 기기 Safari에서 로컬 정적 QA 빌드를 실행했다. 시뮬레이터나 데스크톱 viewport가 아니다. **첫 3분 측정은 성능 미달**이며 전체 게임·아트 합격은 아니다.

## 첫 실측: 유리 투과 패스 전체 해상도

[원시 전체 프레임 및 출처](device-qa/evidence/iphone-full-transmission.json), [실제 기기 7장](device-qa/captures/full-transmission/report.json), [재현 도구](device-qa/README.md).

| 항목 | 실제 결과 |
|---|---|
| 측정 시각 UTC | 2026-09-24 17:20:15.496 → 17:23:15.543 |
| 연속 rAF 측정 | 180.018초 / 5,793구간 |
| 평균 / P95 / 최대 간격 | 32.1801fps / 36ms / 61ms |
| 렌더 오류 / 화면 숨김 | 측정 중 각각 0회 |
| CSS / 원래 DPR / 렌더 buffer | 440×796 / 3 / 880×1592 (상한2) |
| 모델 / visible triangles / draw calls | 4개 / 105,096 / 33 |
| 판정 | P95 ≤33.3ms 미달, 60fps 목표 미달 |

출발 HEAD는 `27fc24446bb13e1aceb29d1b1b9cb3a4c770f3bb`이며 카세트 균열·투명도 수정의 미커밋 소스를 포함했다. JSON의 모든 빌드 입력 해시와 측정 후 해시가 일치한다. 실제 OS는 Xcode 정보이며, Safari UA에 호환용으로 표시된 `iPhone OS 18_7`을 OS 버전으로 사용하지 않았다. USB CoreDevice 터널의 Mac 쪽 IPv6 주소로 연결했다. 기기 이름·UDID·일련번호는 기록에서 제외했다.

20초씩 세 물건의 검사/압착/파손과 보관을 직접 주입하는 fixture다. 전체 게임 명령·손가락 입력을 실행한 것이 아니다. 구간별 P95는34–36ms이며 특정 한 장면에서만 느린 현상은 아니었다. 촬영은 3분 측정이 끝난 뒤 수행했다. 실제 캡처에서 카세트의 정상 호박색 유리와 큰 파손 구멍·내부 축 노출을 확인했다. 작은 균열의 사용자 인지·실사 품질 합격으로 확대하지 않는다.

## 재측정 시작 중 별도 실패

유리 투과 중간 영상만 CSS 해상도로 바꾸고 정적 빌드를 다시 열자 `WebGL context lost`가 한 번 발생했다. [시작 실패 기록](device-qa/evidence/iphone-css-transmission-startup-failure.json)을 보존했다. 3분 측정은 시작하지 못했고, 오류 후 표시된 rAF 60fps는 렌더 성공의 증거가 아니다. 기존 테스트 탭의 GPU 자원 잔존과 설정 변경 중 어느 쪽 영향인지 아직 분리하지 않았다. 이 최적화의 성능 개선·실기기 통과를 주장하지 않는다.

같은 빌드를 새 세션으로 다시 열었을 때는 정상 로드됐고 아래3분 측정을 완료했다. 앞선 실패 원인은 아직 확정하지 않았다. 기기 Safari의 Web Inspector가 꺼진 상태를 도구에서 확인했고, 추가 원인 분리를 위한 활성화를 사용자에게 요청했다. 성공한 한 실행으로 시작 실패를 해소했다고 판단하지 않는다.

## 조정 후 실측: 화면 DPR2 유지, 유리 투과 영상만 CSS 해상도

[원시 전체 프레임 및 출처](device-qa/evidence/iphone-css-transmission.json), [기기 비교 캡처7장](device-qa/captures/css-transmission/report.json).

`resize`에서 Three.js의 `transmissionResolutionScale`을 `1/dpr`로 설정했다. 기기의 화면·금속 표면·유리 경계·UI 해상도를 내리지 않고, 유리 너머 굴절에 사용되는 중간 영상만 CSS 해상도로 그린다. 원본 에셋·PBR 텍스처·삼각형·조명은 그대로다. 작은 화면의 유리 내부가 덜 선명할 수 있는 교환 조건이 있으므로 전후 기기 캡처를 별도로 남겼다.

| 항목 | 실제 결과 |
|---|---|
| 측정 시각 UTC | 2026-09-24 17:31:26.325 → 17:34:26.345 |
| 연속 rAF 측정 | 180.005초 / 7,210구간 |
| 평균 / P95 / 최대 간격 | 40.0544fps / 29ms / 60ms |
| 렌더 오류 / 화면 숨김 | 측정 중 각각0회 |
| CSS / 실제 렌더 buffer | 440×796 / 880×1592, 이전과 동일 |
| 판정 | P95 ≤33.3ms 충족, 60fps 목표 미달 |

같은9구간 fixture와 동일 모델·OS에서 이전32.18fps→40.05fps, P95 36→29ms를 관측했다. 구간별P95는28–30ms다. 소스 빌드 전/후/측정 종료 해시는 모두 일치한다. 각각1회 측정이며 기기 온도·다른 앱·OS 부하를 완전히 통제한 반복 실험은 아니다. 앞서 발생한 초기 context-loss는 별도 실패로 유지한다. JSON의 `passed: true`는 해당180초의 P95·오류·visibility 조건에만 해당하며 60fps·입력·시각 완성·전반적 안정성 합격은 아니다.

실제 카세트 정상/파손·렌즈 파손·보관 캡처를 열어 확인했다. 큰 파손 구멍과 유리 내부 축·세 보관물은 보인다. 전후 정상 유리의 내부 영상은 작은 차이가 있으므로 동일 픽셀이나 무손실 최적화라고 표현하지 않는다. 기기 방향 API로 가로를 요청했지만 응답과 Safari viewport는 세로 그대로였고 resize 이벤트가 없었다. 원래 세로를 다시 지정했으며 실제 가로 회전 검증은 미완료다.

## 추가 B 렌더러 점검

1. `role/b-render`의 검사할 commit SHA를 기록한다. `npm ci`, `npm run check` 후 `npm run dev -- --host 0.0.0.0`으로 개발 서버를 연다. 같은 신뢰할 수 있는 로컬 네트워크의 실제 iPhone Safari에서 `http://<개발 Mac의 LAN 주소>:5173/docs/handoffs/B/preview.html`을 연다. 공개 터널이나 배포는 필요하지 않다.
2. 모델명, iOS 버전, Safari 버전, 세로/가로, 화면 CSS 크기와 DPR을 기록한다. 이 페이지 상단에 **RENDER STUDY / NOT GAMEPLAY**가 보여야 한다. 네 모델과 새 계기판이 로드되는지 확인한다.
3. 세 회수품을 각각 검사·압착·파손 상태로 전환한다. 압력 0/50/100%에 계기판 바늘이 왼쪽/위/오른쪽을 가리키는지, 렌즈 파손 조각·금속/복합재 변형·누름판 접촉·케이스 3칸 안착을 캡처한다. 화면 회전 뒤 검은 화면이나 잘림이 없는지 확인한다.
4. 상단 FPS/P95는 **최근 600 프레임** 값이다. 이를 3분 전체 통계로 옮겨 적지 않는다. 연속 프레임 전체 기록과 기기 실측이 없는 동안 PRD의 3분 기준은 미검증으로 유지한다. 데스크톱 `soak-check.mjs`의 결과를 기기 결과로 재사용하지 않는다.

## 통합 후보에서 완료할 검증

A/C의 실제 게임이 합쳐진 후보 commit에서 3분 연속 플레이로 검사 → 압착 → 손 떼기 → 정착 → 보관 → 실패/정산 → 재시작을 수행한다. 입력 취소·앱 전환·복귀·다중 터치를 함께 확인한다. 목표는 60fps, 전체 프레임 간격의 P95 ≤33.3ms, 강제 새로고침·검은 화면·입력 고착 0회다. fixture의 수동 상태 선택은 이 전 과정을 대신하지 않는다.

기록에는 commit, 실제 기기/OS/브라우저, 시험 시작·종료 시각, 전체 측정 시간·표본 수·FPS/P95, 오류 및 재현 방법, 실제 캡처, 검사자를 포함한다. 결과가 없으면 빈 숫자를 0으로 채우거나 `verified`로 올리지 않는다. 위 실측과 구분해 추가 기기·통합 후보의 결과를 이어서 기록한다.
