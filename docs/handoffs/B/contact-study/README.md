# 실제 받침면·램·카세트 접촉 조사

2026-09-24. **기존 카세트가 받침 위에 8–12cm 떠 있다는 가설은 실제 geometry와 맞지 않는다.** 카세트는 램 중심과 거의 일치하고 넓은 받침판의 뒤쪽에 놓여 있다. 원래 Y 배치는 일부 하부가 약 5mm 받침에 들어간다. 원본 목표와 다른 깊이·구도 문제를 해결하려고 카세트 Y를 크게 내리면 geometry를 관통한다.

수치 기준은 [measurement.json](measurement.json), 재현 코드는 [measure.mjs](measure.mjs)다. 변경 범위는 이 디렉터리뿐이며 모델·production renderer·ram을 수정하지 않았다. 이는 **원위치 GLB의 기하 검사**다. 실제 WebGL 시각 품질, 동적 변형, 물리 안정성, iPhone 검증과 구분한다.

## 방법과 입력

- 최종 runtime `press-chamber.glb`의 `press-frame`, `press-ram`과 `salvage-cassette.glb`의 실제 indexed triangles를 직접 읽었다. GLB node에 별도 transform이 없음을 확인했다.
- 단위는 m, asset root의 +Y up / +Z front. 재질 normal map이 아니라 **triangle의 기하 법선**을 사용했다.
- 받침에는 Y=.48에서 아래로 수직 ray, 램과 카세트 하부에는 아래쪽 첫 교차를 계산했다. XZ 2.5mm 간격의 209×249 grid를 triangle 내부 barycentric 좌표로 평가했다. 이 grid는 연속 충돌 판정의 완전한 증명이 아니다.
- 별도로 세 지점의 결과를 Three.js `Raycaster`와 교차 검증했다. 차이는 최대 약 5.6e-17m였다.
- 기준 배치는 기존 anchor `(0.0214740932, 0.3687374294, -0.0936739240)`에 clearance `.003`을 더한 baseY `.3717374294`다. 조사 중 root가 별도로 변경한 최신 renderer 상태라고 가정하지 않는다.

| 입력 | SHA-256 |
|---|---|
| press-chamber.glb | `fae32ad1874c35a03682135303922f33d35a60d9bb8c5648f8921634ec07cc75` |
| salvage-cassette.glb | `5ef39a75ca73bf6de45605d32b09099ff66710fa0e009eacca1da9d55c704aee` |

카세트를 포함한 전체 입력 해시는 JSON의 `inputs`에 기록했다. 재질과 생성 원본을 바꾸지 않았다.

## 받침은 어디에 있는가

상면 후보는 ray의 가장 높은 교차 중 Y `.367–.390`, 기하 법선 Y `>.97`인 표본이다. 완벽한 수학 평면이 아니라 완만하게 기울고 모서리·홈이 있는 생성 mesh다. 아래 범위는 2.5mm 표본 해상도의 근사다.

| 대상 | X 범위 | Z 범위 | Y 또는 중심 |
|---|---|---|---|
| 받침의 넓은 상면 후보 | −.1800…+.1925 | −.2100…+.2925 | Y .368026… .379530, 중앙값 .373718 |
| 같은 상면의 면적 중심 | .008746 | .041364 | .373872 |
| 램 실제 저면 footprint | −.1300…+.1700 | −.2250…+.0375 | Y 중앙값 .551472 |
| 램 저면 footprint 면적 중심 | .020874 | −.094721 | .551545 |
| 기존 anchor 바로 아래 실제 면 | .021474 | −.093674 | **.376368** |

받침의 상면 중심보다 램 중심이 약 **136mm 뒤쪽(−Z)**이다. 기존 anchor XZ는 램 footprint 중심에서 X 약 .6mm, Z 약 1.05mm 차이여서 램 정렬 자체는 맞다. 받침 전체의 중앙과 램 중심은 동일한 위치가 아니다.

중앙 X=.021474에서 실제 높이는 Z=−.20일 때 .378650, Z=0일 때 .374638, Z=+.20일 때 .370986m다. 앞쪽으로 완만하게 내려가는 넓은 받침이다. Z=−.225에서는 받침 뒤의 낮은 영역 Y≈.327로 떨어진다. `Box3`의 전체 중심이나 화면에서 보이는 앞쪽 모서리를 상면 접촉 좌표로 쓰면 이 차이를 놓친다.

## 현재 카세트의 실제 하부 간격

카세트 GLB 전체 bounds는 X ±.140, Z ±.069239, Y 0… .134282m다. 이 bounds의 Y=0 평면 전체가 실제 바닥 면은 아니다. 하부가 둥글고 울퉁불퉁하므로 실제 하부 ray와 받침 ray의 차이를 사용했다.

| 배치 | 최소 하부 gap | gap 중앙값 | 램 footprint 안 투영 비율 | 침투 표본 |
|---|---:|---:|---:|---:|
| 원래 XZ, scale1, yaw .45, base .371737 | **−4.770mm** | +3.844mm | 99.96% | 788 / 5,502 |
| 원래 XZ, scale1, yaw0, base .371737 | −5.170mm | +3.639mm | 100% | 715 / 5,505 |
| Z만 0으로 이동, scale1, yaw .45 | −3.033mm | +5.661mm | **64.34%** | 278 / 5,505 |
| Z만 +.03으로 이동, scale1, yaw .45 | −2.473mm | +6.313mm | **43.40%** | 171 / 5,505 |
| root 제안: 원래 XZ, scale1.1, yaw .45, base **.376737** | **+.173mm** | +9.701mm | **96.91%** | **0 / 6,666** |

음수는 이 표본에서 기하 관통, 양수는 해당 XZ에서 하부와 받침 사이 간격이다. gap 중앙값이 양수여도 실제 최저점이 닿으면 물체가 평판 전체에서 뜬 상태는 아니다. 반대로 하부의 일부 점이 맞는 것만으로 접촉 그림자나 시각적 착지가 충분히 설득력 있다고 판단하지 않는다.

램 투영 포함 비율은 “램 하단 아래에 놓인 카세트 실루엣 면적 비율”이다. 힘의 분포·안정성·충돌 통과율이 아니다. scale1.1의 .45rad 자세는 대부분 램 아래지만 모서리 일부는 밖으로 나간다. 카세트만 넓은 받침의 중앙으로 옮기면 램 정렬을 크게 악화시킨다.

## 높이 수정 권고

**XZ는 유지하고, 기존 baseY를 약 +5mm 올리는 방향이 수치와 맞다.** root 제안의 `workbedY=.3737374294` + clearance `.003` = base `.3767374294`는 scale1.1/yaw .45에서 최소 gap +.173mm이고 침투 표본이 없었다. 이 수치에서 상면이 실제로 .373737이라는 뜻은 아니다. anchor 아래 상면은 .376368이며, 해당 변수는 최종 base를 만들기 위한 보정값으로 사용되는 것이다.

회전까지 고려하면 한 자세에 맞춘 Y를 보편적 접촉값으로 간주할 수 없다. 15° 간격 24 yaw의 결과는 다음과 같다.

| 크기 | 표본 침투를 없애는 최소 baseY 범위 | 램 투영 포함 비율 범위 |
|---|---|---|
| scale1 | .375621… .377641m | 97.97…100% |
| scale1.1 | .375597… .377845m | 88.63…98.57% |

따라서 scale1.1 전체 회전 표본에 하나의 고정 Y를 쓰려면 **base .3780–.3783m** 정도가 보수적인 시작점이다. `.376737` 고정값은 검사한 yaw 중 최대 약 1.11mm 관통할 수 있다. 이 범위는 2.5mm ray grid와 15° yaw 표본에 한정하며 연속 회전 무관통 보증은 아니다. 한 점의 ray height나 `bounds.min.y`만으로 완전한 지지면을 계산했다고 보고하면 안 된다.

Y 보정 후에는 램의 travel clamp·접촉 상단 계산과 접촉 그림자 위치도 같은 기준으로 확인해야 한다. 눌림 셰이더를 적용한 하부, 다른 회수물, entity의 비균일 scale/회전, 테이블 clip은 이 조사에서 계산하지 않았다.

## 기존 높이 오차의 근거

기존 `prepare_mobile.py`는 `sourceBedSampleBoxBlender` 안에 들어온 vertex의 최대 높이를 취한다. 그 3D box를 기록된 원점·축·scale로 glTF 좌표로 바꾸면 다음과 같다.

```text
X [-.115291, +.150662]
Y [ .313224,  .371040]
Z [-.115366, +.058082]
```

이 box의 Y 상한 **.371040**이 실제 받침보다 낮다. 같은 XZ 범위의 수직 ray 상면 중 **99.27%가 이 상한 위**이며 중앙값은 .375048이다. anchor 지점의 상면 .376368도 제외된다. 이 때문에 낮은 모서리 vertex를 “상면 최대 높이”로 고른 것으로 해석된다. 이는 원래 코드·box 정의와 현재 runtime triangle의 대조에 근거한 원인 설명이며, 원본 generation 단계의 모든 변환을 다시 실행한 결과는 아니다.

## 재현

```sh
node docs/handoffs/B/contact-study/measure.mjs
```

출력 `measurement.json`은 좌표·24각도 표본·입력 해시를, `heightfields.json`은 실제 ray 높이 배열을 보존한다. 모든 값은 3D 기하에서 계산했으며 이미지의 픽셀 위치를 역산해 만든 접촉값이 아니다.
